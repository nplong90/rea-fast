# REA-Fast acceptance gate — evidence and functional parity

Two different gates exist: **M1** is a hardening merge that preserves explicit
*partial* compatibility and requires zero reachable P0/P1 issues plus proof for
every capability advertised as supported. **M2** is the full upstream drop-in
parity release described below and remains blocked. Do not describe a passing
M1 test run as M2 success. The versioned 245-route inventory is
[`route-contracts.json`](route-contracts.json). It is regenerated by
`node tests/acceptance/contracts.mjs --write`, and `--check` enforces that
it stays in sync with catalog, routing declarations and positive MCP fixtures.
`fixture-backed-candidate` means a qualifying narrow black-box assertion, not
upstream-equivalent semantics; `experimental` is not supported at M1.
`node tests/acceptance/provider-offline.mjs --rust-bin target/debug/rea-fast`
also checks that the 53 provider-dependent routes do not invent successful
external-provider results when PATH contains no external CLIs (51 negative
probes; 2 host `/proc` routes require a live host and are explicitly excluded).
This check does **not** prove real ADB, Rizin, Frida or JEB operations work.

Target: REA-Fast may be released as **functionally equivalent to upstream REA** only after all required 245-tool contracts have a verified route, a reproducible fixture with observed output, an upstream reference result for matching scope, and passing cross-platform/security tests. A native dispatch entry is *not* proof of readiness; a live fixture is *not* proof of semantic parity. Some native fixtures only assert correct negative detection or narrow static metadata; full real-world positive coverage remains open.

Run `node tests/acceptance/mcp-matrix.mjs --rust-bin target/debug/rea-fast`. The script starts the real MCP binary in full-profile mode, retrieves all 245 tools through both `tools/list` and `rea_search_tools`, validates uniqueness and routing metadata, executes 63 narrow native catalog fixture contracts plus one noncatalog extension (65 fixture executions in total), and saves a per-tool JSON manifest in `acceptance-artifacts/`. The CI executes this on Ubuntu **and** Windows and archives the manifests even on failures.

Matrix states: `not_tested` means no qualifying runtime fixture; `fixture_exercised` means the stated specific assertions passed. **Every row still has `upstream_parity: not_verified`** until a separate matched upstream comparator proves the same semantic contract. The report is deliberately `partial_acceptance` while substantial functionality remains unverified.

**M2 full-equivalence release gate:** pass only if the required feature manifest has no `unavailable`, `not_tested`, `not_comparable` or `unverified` entries; full Evidence graph, provider lifecycle, security, and equivalent-output CPU/RSS/time must be verified. The current quality workflow is a regression gate, not a full release certificate. Do not claim full REA replacement while this release gate is blocked.

The report separately lists `additional_routes_exercised` for callable REA-Fast extensions **absent from the 245-tool catalog**. These are not counted toward catalog readiness. Such entries reveal tool-discovery gaps and need an explicit publication decision; no fixture pass is promoted to upstream parity.
